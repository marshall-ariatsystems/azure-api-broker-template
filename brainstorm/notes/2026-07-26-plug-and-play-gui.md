# Plug-and-play broker and GUI

- 2026-07-26: Planning resumed on `dev` branch. Goal: make end-user setup near-zero and make required configuration understandable through a GUI.
- Product evidence: current `admin-ui` can write Key Vault secrets, edit role mappings, probe vendor reachability, and restart the broker, but assumes Azure resources, Entra roles, local config, Node/npm, and `az login` are already in place.
- Existing reliability mechanisms: Table Storage-backed caller/key quotas with 429 + Retry-After; oauth2cc token cache, expiry refresh, and one 401 re-mint retry; bridge refreshes Entra token two minutes before expiry.
- Open thread: define the privileged administrator setup wizard versus the end-user launcher, including what belongs in the GUI and what must remain an Azure/Entra administrator action.
- 2026-07-26: Direction set: target any API-consuming organization or individual, not only internal IT teams. Azure must become an implementation/provider option rather than the product mental model. The user-facing experience should be vendor, cloud, and credential-system agnostic.
- 2026-07-26: Local deployment is acceptable. Local use must require a FIDO2 hardware key, but implementation of that constraint is deferred. Immediate focus is identity-provider authentication and permission scopes.
- Clarification: this product centralizes *who may use a vendor API key*, not what the key itself may do at the vendor. The identity gate maps approved people/workloads to a broker-held API-key connection; the broker injects the full vendor credential and does not attempt vendor-side request or permission-scope enforcement. No user receives the raw key.
- Working direction: use an identity-provider abstraction with standards-based OIDC/OAuth authorization-code-with-PKCE support. Normalize IdP users, groups, and workload identities to connection-access grants in an admin policy UI. Product language is “who can use this connection,” not cloud-provider-specific app roles or vendor permission scopes.
- 2026-07-26: User requested a phased path to a first product-package release. Corrected deployment model: the local package is stateless and stores no API credentials, connection profiles, refresh tokens, or other persistent product data. It connects directly to the configured identity provider, or is registered as an application in that provider, and uses ephemeral tokens to reach the remotely hosted broker. Secret storage is a remote broker/secret-provider responsibility; local hosting is deferred. FIDO2-only remains a release gate. No vendor-level scope enforcement is in scope.
- Distribution/onboarding direction: provide an IdP-specific registration package when the broker app is not already registered, and publish verified prebuilt integrations in relevant IdP marketplaces where available. The registration package contains only non-secret IdP metadata/policy: redirect URIs, broker resource/audience, requested claims/groups, FIDO2 assurance requirement, and access-grant bootstrap. The same stateless local client package is used across IdPs; it should not have a client secret.
